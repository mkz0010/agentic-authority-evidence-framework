# Minimal Use Guide

Status: Non-normative entry-point guide.

This guide is the first stop for readers who want to understand and use AAEF framing in a design review or assessment conversation.

It is intentionally small.

It does not replace the full framework, control catalog, evidence schema, assessment artifacts, testing procedures, or claim-boundary documents.

It does not update the active control and assessment baseline.

The active baseline remains AAEF v0.4.1 unless a later release explicitly updates the control catalog, evidence schema, assessment artifacts, or testing procedures.

AAEF v1.0.0 remains a conservative release path planning release.

## What this guide is for

Use this guide when you want to have a first AAEF-based conversation about an AI agent action.

This guide helps a reviewer ask:

- what action is being requested
- who or what is requesting it
- on whose behalf it is requested
- what authority or scope applies
- whether execution is checked at the point of dispatch or backend use
- what evidence would support later reconstruction
- what AAEF does not prove

This guide is useful for a single design review conversation.

It is not a complete AAEF assessment.

## What this guide helps you do

This guide is intended to help a reviewer turn a vague question such as "Can the AI agent do this?" into a more precise review conversation:

- What action was proposed?
- Who or what had authority to request it?
- What boundary decided whether execution was allowed?
- Was the action dispatched or blocked?
- What evidence exists for the decision and outcome?
- What remains uncertain after reviewing that evidence?

The guide does not make the action safe, compliant, authorized, or production-ready by itself. It provides a small entry point for asking the right questions before larger AAEF materials are needed.

## What this guide is not

This guide is not:

- a certification scheme
- a compliance framework
- a conformity assessment
- an audit opinion
- a legal assurance mechanism
- a production-readiness review
- an implementation conformance test
- a control conformance decision
- an evidence sufficiency determination
- an automated risk acceptance process
- an external-framework equivalence claim

Using this guide does not mean that a system is safe, compliant, certified, audit-ready, legally sufficient, production-ready, or fully assessed under AAEF.

## Core thesis

AAEF starts from a simple operational principle:

> Model output is not authority.

An AI model may propose an action.

That proposal is not enough to authorize execution.

Before a meaningful action is executed, a system should be able to show:

- what was requested
- who or what requested it
- on whose behalf it was requested
- what authority or policy was evaluated
- whether the action was allowed at the point of execution
- what evidence supports later review and reconstruction

AAEF focuses on the boundary between model-generated intent and real-world or system-level action.

## The five questions

This guide presents the five questions before the vocabulary on purpose. A new reader should first see the review problem AAEF is trying to make visible. The vocabulary section then provides the minimum terms needed to discuss those questions more precisely.

Use these five questions in the first review conversation.

| Question | Plain-language review use |
| --- | --- |
| Who or what acted? | Identify whether the model, agent runtime, tool gateway, backend service, human operator, or another component performed or blocked the action. |
| On whose behalf? | Identify the principal, user, organization, role, delegated authority, or operational context associated with the requested action. |
| With what scope or authority? | Identify what policy, approval, delegation, credential reference, or boundary was supposed to authorize the action. |
| Was the action allowed at execution time? | Check whether authorization was evaluated close to dispatch or backend execution, not only earlier in the prompt or plan. |
| What evidence supports reconstruction? | Identify records that link request, decision, dispatch or non-dispatch, result, review context, and remaining uncertainty. |

These questions are review prompts.

They are not a full assessment procedure by themselves.

## Minimal vocabulary

The full AAEF vocabulary is larger than this guide.

For a first review conversation, the following terms are enough.

### Model output

Text, structured data, plan, tool call proposal, or other output generated by a model.

In AAEF, model output can express intent or a proposed action, but it is not authority by itself.

### Action request

A normalized request to perform an action.

A useful action request should identify the requested action, target, parameters, principal context, purpose, risk level, and any credential reference or scope boundary.

### Authority

The permission, delegation, policy, approval, role, or other basis that could allow an action to proceed.

Authority should be evaluated by a trusted component, not merely asserted by the model.

### Principal

The user, account, organization, role, service, or other entity on whose behalf an action is requested or performed.

Principal context matters because an action may be safe for one principal and unauthorized for another.

### Authorization decision

A decision that allows, denies, holds, expires, or otherwise constrains a requested action.

A useful authorization decision should be linked to the specific action request and should include reason, scope, policy or rule version, and timing.

### Tool Dispatch Enforcement Point

The component or boundary that prevents a tool call, API call, backend operation, or other action from executing unless the required decision and scope are present.

This is where model intent should be separated from executable authority.

### Evidence event

A structured record that supports later review or reconstruction.

An evidence event may link request, decision, dispatch, non-dispatch, execution result, reviewer context, and integrity information.

### Non-execution evidence

Evidence that an action was denied, held, expired, revoked, blocked, or otherwise not dispatched.

AAEF treats non-execution as important because a prevented action may matter as much as an executed action.

### Human approval

A human decision or confirmation related to an action.

Human approval is not automatically risk acceptance. Approval quality depends on what the approver saw, what authority the approver had, whether the payload changed, and whether the approval remained within scope.

### Risk owner

The person or organizational function accountable for accepting or rejecting residual risk.

A reviewer should not assume that a human approval click is the same as risk-owner acceptance.

## One action-flow review pattern

This pattern illustrates AAEF framing for one AI agent tool-call decision.

It is not a complete assessment procedure.

It is not a conformance test.

It is not an implementation checklist.

It is not a production-readiness review.

### Scenario

An AI assistant proposes sending an external email with a generated attachment to a customer.

The model output says:

> Send the report to the customer now.

AAEF framing treats this as a proposed action, not as authority.

### Step 1: Convert model output into an action request

The review asks whether the system creates or can reconstruct an action request.

Minimum useful fields include:

- requested action: send external email
- target: customer email address or recipient reference
- parameters: subject, body, attachment reference
- principal: user or organization on whose behalf the email would be sent
- purpose: customer report delivery
- risk level: based on recipient, attachment, sensitivity, and business impact
- credential reference: mail-sending identity or service account reference
- timestamp
- generated-by-model indicator

Review question:

> Can the reviewer see the proposed action as a bounded request rather than only as model text?

### Step 2: Identify required authority

The review asks what authority is required.

Examples:

- Is the principal allowed to send customer-facing email?
- Is the recipient in scope?
- Is the attachment approved for external sharing?
- Does the action require human approval?
- Does the action require a policy check?
- Does the action require a data classification check?
- Does the action require a fresh authorization decision?

Review question:

> What must be true before this action can be dispatched?

### Step 3: Evaluate the authorization decision

The review asks whether a trusted component records a decision.

Possible decisions:

- permitted
- denied
- held for human approval
- expired
- revoked
- not dispatched because evidence requirements were not met

A useful decision record should include:

- linked action request
- decision result
- reason
- policy or rule version
- trusted inputs used
- untrusted inputs excluded
- timestamp
- deciding component

Review question:

> Is there a decision record linked to the action request, or is the system relying on the model's own statement?

### Step 4: Check dispatch enforcement

The review asks whether the tool or backend checks the decision before execution.

Useful questions:

- Does the mail-sending tool verify that the decision matches the action?
- Does the decision expire?
- Is the recipient bound to the decision?
- Is the attachment digest or reference bound to the decision?
- Can the model change the payload after approval?
- Can the agent retry with another tool after denial?
- Is non-dispatch recorded when the action is blocked?

Review question:

> Was execution controlled at the dispatch or backend boundary, not only in the prompt?

### Step 5: Identify evidence for reconstruction

The review asks what evidence exists.

Useful evidence may include:

- model proposal or request source
- normalized action request
- authorization decision
- dispatch or non-dispatch record
- tool result or backend response
- human approval context, if any
- evidence writer or gateway record
- timestamp and correlation identifiers
- remaining uncertainty or evidence gaps

Review question:

> Could a reviewer reconstruct what was requested, decided, dispatched or blocked, and why?

### Step 6: Record what remains uncertain

Uncertainty is structural, not incidental. AAEF evidence can support reconstruction and review, but it does not eliminate all uncertainty about intent, correctness, sufficiency, safety, legal effect, or risk acceptance.

A minimal review should therefore record what remains uncertain instead of treating the evidence record as proof that the action was fully safe, compliant, or acceptable.

AAEF evidence may still leave gaps.

Examples:

- The attachment content may not have been independently reviewed.
- The model rationale may be incomplete or misleading.
- The policy may have been wrong.
- The evidence writer may share the same compromise boundary as the agent.
- A related action may have occurred through another system.
- A human approval may not equal risk-owner acceptance.

Review question:

> What does the evidence not prove?

## Minimal review output

For a first conversation, a reviewer can summarize the result in a small table.

The following table condenses Steps 1-6 into a single discussion artifact. It is not a complete AAEF assessment worksheet, conformance test, implementation checklist, or production-readiness checklist.

| Review item | Example answer |
| --- | --- |
| Proposed action | Send external email with attachment |
| Principal | Account or user on whose behalf the assistant acts |
| Required authority | Email-sending scope, recipient scope, attachment release approval |
| Decision point | Authorization gateway or policy decision component |
| Dispatch enforcement | Mail tool or backend checks linked decision before sending |
| Execution result | Sent, denied, held, expired, or not dispatched |
| Evidence | Request, decision, dispatch/non-dispatch, result, approval context |
| Gaps | Payload binding, evidence independence, risk-owner acceptance, compromise boundary |

This table is only a discussion aid.

It is not a complete AAEF assessment result.

## What AAEF evidence does not prove

AAEF evidence supports review and reconstruction.

AAEF evidence does not, by itself, establish:

- legal proof
- legal admissibility
- legal sufficiency
- audit evidence sufficiency
- compliance documentation sufficiency
- factual truth
- model correctness
- action correctness
- policy correctness
- risk acceptance
- implementation conformance
- control conformance
- production readiness
- external-framework equivalence

## One-sentence use

Use AAEF to ask whether an AI-generated action was requested, authorized, bounded, enforced, evidenced, and reviewable.

Do not use AAEF to claim that the action, system, evidence, assessment, or organization is certified, compliant, audit-sufficient, legally sufficient, production-ready, or risk-accepted.
